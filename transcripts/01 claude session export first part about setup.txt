  Steps 1 and 2 are independent of each other, so they run in parallel.

  What a changed input triggers: constraints.md → 3, 4, 5 · CSV → 1, 3, 4, 5 ·
  an interview or the survey → 2, 3, 4, 5.

  Why subagents, and only three

  - data-analyst and qual-researcher: each gets a fresh context with only its
    own inputs. The qual researcher doesn't see the numbers, so it can't bend
    quotes to fit them, and vice versa. Step 3 is where the two meet,
    deliberately.
  - reviewer: a red-team check that has never seen the drafting. It gets the
    output file plus the inputs and nothing else. Reviewing in the same context
    that wrote the draft mostly confirms the draft.
  - Steps 3–5 stay in the main session, because that's where your checkpoint
    answers live.

  Self-checks: two kinds

  1. Deterministic (scripts/check_outputs.py, run after every step). These are
     cheap and can't be talked around:
     - Every number in 03/04 must appear in 01-data-analysis.md. This enforces
       "numbers only from the script".
     - Memo ≤ 600 words.
     - Source tags present.
     - No fear phrases in customer copy.
     - No VERDICT.md written by Claude.
  2. Judgement (the reviewer agent, before each checkpoint). Claude fixes the
     blocking findings itself and shows you the rest. That way you only spend
     checkpoint time on decisions, not on catching errors.

  Two checkpoints only

  CP1 (which problem do we frame) and CP2 (sign-off). These are the two places

❯ why does the analyst get questions to cover and not hypotheses?

⏺ There are three reasons, and one real downside you should weigh.

  Why questions:

  1. Anchoring. Any hypotheses I'd write now would come from what I've already
     read in the interviews, e.g. "phone follow-up drives returns" or "opening
     the report predicts return". An analyst handed "test whether X" tends to
     find X: it picks the cut that confirms it and stops looking. That's the
     same reason the analyst isn't allowed to read the interviews. Data and qual
     are meant to arrive at step 3 independently, so that where they agree it
     means something, and where they disagree it shows up as a contradiction.
  2. The live rerun. If they change the CSV, hypotheses written for today's data
     may simply stop fitting. A coverage list (window, segments, confounders,
     reach, what the data can't show) stays valid whatever the data says.
  3. It isn't quite hypothesis-free. The list already holds my judgement about
     what matters: which confounders to cross-check (follow-up × location type,
     consent × location type), and "reach", because a recommendation that can
     legally reach 20% of customers is a different decision from one that
     reaches 80%.

  The downside: an open list invites fishing. Seven segment variables give
  dozens of cells, and some will look striking by chance. Hypotheses would force
  the analysis to be falsifiable and focused.

  A middle path I'd recommend: the analyst writes down its own expectations
  before running the script ("I expect X, because Y"), then reports which held
  and which didn't. That's lightweight pre-registration: it gets the
  falsifiability without me planting the hypotheses. The second half of the loop
  already exists: in step 3, if a mechanism from the interviews needs a number
  the analysis doesn't have, CLAUDE.md requires extending the script, so the
  qual hypotheses do get tested, just after both sides have looked
  independently.
